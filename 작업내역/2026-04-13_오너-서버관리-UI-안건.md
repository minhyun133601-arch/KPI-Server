# 오너 전용 서버 관리 UI 안건 / Owner Server Management UI Proposal

작성일 / Date: `2026-04-13`
상태 / Status: `proposal phase`

## 1. 목표 / Goal

- KR: `명령어/` 폴더에 있는 운영 명령을 오너 전용 화면의 `서버 관리`에 연결해서, 서버 PC에서 직접 `.cmd`를 찾지 않아도 주요 운영 작업을 실행하기 쉽게 만든다.
- EN: Expose the operational commands in `명령어/` through the owner-only `서버 관리` screen so the owner can run the main server operations without browsing `.cmd` files on the server PC.

## 2. 결론 / Conclusion

- KR: **가능하다.**
- KR: 다만 `브라우저에서 임의의 cmd/powershell을 실행하는 구조`로 가면 안 된다.
- KR: `allowlist 기반의 서버 작업 실행기`와 `폼/API 기반의 계정 관리 기능`으로 나눠야 한다.
- EN: **This is feasible**, but not as arbitrary shell execution from the browser. The safe design splits into an allowlisted server-task runner plus form/API-based account management.

## 3. 현재 확인한 전제 / Current Findings

- KR: 오너 전용 섹션에는 이미 `서버 관리` 카테고리 placeholder가 있다.
  - `06_★★★_KPI런타임/sections/KPI.sections.owner.js`
- KR: 오너 전용 API 표면은 이미 존재한다.
  - 예: `GET /api/owner/access-overview`
- KR: `명령어/` 폴더의 `.cmd`는 대부분 `06_★★★_KPI런타임/internal-server/scripts/windows/*.ps1` 또는 내부 서버 스크립트로 연결되는 래퍼다.
- KR: 일부 명령은 `대화형 콘솔` 또는 `비밀번호 입력`을 전제로 하므로 버튼 래핑만으로는 UI 품질과 보안 경계를 만족시키기 어렵다.

## 4. 명령어별 분류 / Command Classification

### 4-1. 1차 UI 래핑 가능 / Good Phase-1 Candidates

다음 명령은 `버튼 + 상태 + 실행 로그` 형태로 비교적 안전하게 UI에 올릴 수 있다.

1. `01-부팅시-자동실행-등록.cmd`
2. `02-부팅시-자동실행-해제.cmd`
3. `03-서버-열기.cmd`
4. `04-서버-닫기.cmd`
5. `05-서버-상태-확인.cmd`
6. `12-DB-테이블-보기.cmd`

권장 방식:

- KR: 서버에서 허용된 작업 키만 실행한다. 예: `register_autostart`, `stop_server`
- KR: 브라우저는 작업 키만 보내고, 실제 파일 경로와 실행 명령은 서버 내부 manifest에서 고정 매핑한다.
- KR: 실행 결과는 `표준 출력 요약 + 성공/실패 + 실행 시간 + 실행자`만 보여준다.

### 4-2. 직접 cmd 래핑보다 웹 폼/API로 재구성해야 함 / Rebuild as UI + API

다음 명령은 기존 interactive script를 그대로 실행하는 것보다, 기존 서비스/저장소 경계를 살린 웹 기능으로 만드는 편이 맞다.

1. `06-오너-생성.cmd`
2. `07-일반직원-생성.cmd`
3. `08-비밀번호-재설정.cmd`
4. `09-사용자-삭제.cmd`

이유:

- KR: 입력 항목이 많고, 비밀번호/확인 입력/삭제 확인 문구 같은 폼 검증이 필요하다.
- KR: 감사 로그, 권한 확인, 에러 메시지, 재시도 UX를 웹에서 직접 다루는 편이 낫다.
- KR: 대화형 PowerShell 프롬프트를 원격 브라우저로 중계하는 방식은 유지보수성과 보안성이 떨어진다.

권장 방식:

- KR: 오너 생성은 bootstrap 상태와 연결된 별도 guarded flow로 유지
- KR: 직원 생성/비밀번호 재설정/사용자 삭제는 owner-only POST endpoint + service 호출로 구현
- KR: shell script는 로컬 서버 PC 운영용 fallback으로만 유지

### 4-3. 그대로는 부적합 / Not a Good Direct Web Mapping

1. `11-DB-콘솔-열기.cmd`

이유:

- KR: 이 명령은 `psql` 대화형 콘솔을 연다.
- KR: 브라우저 버튼으로는 `터미널 세션`을 자연스럽게 제공하기 어렵고, 잘못하면 DB 임의 명령 실행 UI가 된다.
- KR: owner 전용 화면에는 `DB 테이블 목록`, `기본 조회`, `연결 상태`, `최근 백업/마이그레이션 상태` 같은 제한된 읽기 기능이 더 적합하다.

권장 대체안:

- KR: Phase 1에서는 `12번`만 노출
- KR: 이후 필요 시 `read-only DB inspect panel`을 별도 안건으로 분리

## 5. 권장 구조 / Recommended Architecture

### 5-1. UI 레이어 / UI Layer

- 위치:
  - `06_★★★_KPI런타임/sections/KPI.sections.owner.js`
  - 오너 전용 런타임 파일 분리 권장
- 역할:
  - 서버 관리 카드 목록 렌더링
  - 위험 작업 확인 모달
  - 최근 실행 결과 표시
  - 실행 중 상태와 마지막 결과 표시

### 5-2. Route 레이어 / Route Layer

- 예시:
  - `GET /api/owner/server-commands`
  - `POST /api/owner/server-commands/:commandKey/run`
  - `GET /api/owner/server-commands/history`
- 역할:
  - owner 권한 확인
  - 입력 검증
  - service 위임

### 5-3. Service 레이어 / Service Layer

- 역할:
  - 작업 allowlist 관리
  - 동시 실행 정책
  - destructive command confirmation token 확인
  - 감사 로그 기록
  - 결과 표준화

예시 반환 모델:

```json
{
  "ok": true,
  "commandKey": "server_start",
  "status": "completed",
  "exitCode": 0,
  "startedAt": "2026-04-13T08:00:00.000Z",
  "finishedAt": "2026-04-13T08:00:12.000Z",
  "summary": "SERVER UP",
  "outputPreview": ["..."]
}
```

### 5-4. Infra 레이어 / Infra Layer

- 새 모듈 예시:
  - `internal-server/src/services/owner-server-commands.js`
  - `internal-server/src/lib/windows-command-runner.js`
- 규칙:
  - KR: 브라우저 입력으로 파일 경로나 셸 문장을 만들지 않는다.
  - KR: `commandKey -> fixed executable/fixed args/fixed cwd` 정적 매핑만 허용한다.
  - KR: timeout, stdout/stderr capture, exit code, concurrency lock를 포함한다.

## 6. 보안 경계 / Security Boundaries

1. owner 전용 인증 필수
2. allowlist 없는 명령 실행 금지
3. 파일 경로를 사용자 입력으로 받지 않음
4. destructive 명령은 2차 확인 필요
5. 실행 결과 로그에 비밀번호/토큰 출력 금지
6. 감사 로그에 `누가`, `언제`, `무슨 작업`, `성공/실패` 기록
7. 서버 열기/닫기처럼 서비스 상태를 바꾸는 작업은 중복 실행 잠금 필요

## 7. 권장 UX / Recommended UX

### 기본 화면

- `서버 상태`
  - 현재 상태
  - 마지막 health check 시각
  - 포트/기본 URL

- `운영 작업`
  - 서버 열기
  - 서버 닫기
  - 상태 확인
  - 자동실행 등록
  - 자동실행 해제

- `계정 관리`
  - 오너 생성 상태
  - 직원 생성
  - 비밀번호 재설정
  - 사용자 삭제

- `DB 보기`
  - 테이블 목록 조회
  - 최근 결과 복사

### 위험도 구분

- 낮음: 상태 확인, 테이블 보기
- 중간: 서버 열기, 자동실행 등록/해제, 비밀번호 재설정
- 높음: 서버 닫기, 사용자 삭제, 오너 bootstrap

## 9. 구현 시 피해야 할 것 / Anti-Patterns

- 브라우저에서 임의 PowerShell 명령 입력 받기
- `.cmd` 경로를 요청 바디로 받아 실행하기
- owner UI에서 raw `psql` 콘솔 노출하기
- 비밀번호를 query string, 로그, CLI history에 남기기
- 기존 `owner-routes.js`나 `server.js`에 모든 실행 로직을 몰아넣기

## 10. 수용 기준 / Acceptance Criteria

다음 조건을 만족하면 안건을 구현 단계로 넘길 수 있다.

1. owner-only UI entry가 존재한다.
2. allowlist 기반 실행만 가능하다.
3. 각 명령 실행 결과가 성공/실패/요약으로 표준화된다.
4. 위험 작업은 확인 절차가 있다.
5. 감사 로그가 남는다.
6. 계정 관리 작업은 shell prompt가 아니라 웹 폼/API를 사용한다.
7. `11-DB-콘솔-열기.cmd`는 direct web execution 대상에서 제외하거나 별도 승인 안건으로 분리한다.
